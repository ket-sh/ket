# The advisor

Date: 2026-08-04. Status: approved. Lands in the same pull request as the
name fix, by the owner's call.

## Why

A dependency arrives carrying rules and know-how. The gates bundle already
names each arrival once, at session start, and sends the session to the
`mechanical-checks` skill for the rules half. Nothing proposes the other
half: the skill that teaches the library's own craft. And an arrival
mid-session goes unnoticed until the next session starts.

## What exists already

- `ket gate toolchain` runs at session start, diffs the manifest against
  what the preset shipped and what earlier sessions saw, and names each
  arrival exactly once. `.ket/toolchain.json` is the record.
- The `mechanical-checks` skill carries the method for the rules half:
  find the checker, judge whether it earns its cost, and propose it.
  ket proposes, the user decides.
- The `find-skills` skill searches for an installable skill.
- Create installs skills through the skills CLI and records them in
  `skills-lock.json`.

## The proposal grows a second half

The toolchain reply names both routes. For each arrival the session
researches the mechanical rule through `mechanical-checks`, as today, and
searches for a matching skill through `find-skills`, proposing what it
finds. A yes applies the choice: the check lands in the config the judge
named, and the skill lands through the skills CLI, with `skills-lock.json`
recording it. The user decides each proposal on its own.

## The look happens when the dependency lands

- The gates bundle adds two PostToolUse entries running the same
  `ket gate toolchain`: one over Bash, filtered through the hook `if`
  field to `bun` commands, and one over Write and Edit, where a manifest
  edit lands. The seen record already makes the gate name an arrival
  once, so every other run stays silent. An arrival neither entry saw,
  as when a merge brings one, still lands at the next session start.
- The gate reads the envelope's `hook_event_name` and answers in that
  event's shape: session start keeps today's reply, and PostToolUse
  carries the same text as its own `additionalContext`.
- The reply stays a proposal the user decides. Declining one proposal
  skips that proposal alone, in the shape `astro add` set for staged
  consent.

## Out of scope

- A decision other than a dependency: an architecture record, a new file
  kind. That slice needs its own trigger and its own spec.
- A curated dependency-to-skill table. `find-skills` searches live, and a
  table inside ket would rot.
- Changing what `mechanical-checks` teaches. The method stays. Only the
  trigger widens.
